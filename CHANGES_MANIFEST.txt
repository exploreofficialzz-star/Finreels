FinReels — Round 12 — Search grey screen root-cause fix
=========================================================
2 files. Extract into project root, overwriting at the same paths.

ROOT CAUSE (confirmed by reading the element tree in main.dart):
  The widget tree is:
    MaterialApp → Navigator → Overlay
      ├── OverlayEntry (route '/') → _SplashGate → MultiProvider → _AppRoot → MainShell
      └── OverlayEntry (pushed route) → ContentSearchScreen  ← NO MultiProvider here

  MultiProvider is INSIDE the initial route's OverlayEntry, not above the
  Navigator. Routes pushed with Navigator.push() create new OverlayEntry
  nodes that are SIBLINGS of the initial route — they have no MultiProvider
  ancestor. context.read<FeedProvider>() inside ContentSearchScreen.initState()
  therefore throws "Could not find the correct Provider above this Widget",
  which causes the late final _feedProvider to never be initialized.
  Subsequent accesses to _feedProvider in build() throw LateInitializationError.
  Flutter catches unhandled build errors and renders a grey error surface —
  exactly what the screenshot showed.

  All other screens that work either use singletons (EngagementService.instance,
  AdService.instance) or are rendered inline as tab content (BlogFeedScreen,
  BooksTab) — never pushed as routes. ContentSearchScreen was the only pushed
  route that called context.read() in initState().

THE FIX (2 files):

lib/screens/content_search_screen.dart
  - ContentSearchScreen now accepts `required FeedProvider feedProvider` as a
    constructor parameter. The `const` keyword is retained (FeedProvider is
    passed as a non-const parameter, which is fine — the widget still benefits
    from const at the class level for its other fields).
  - The `late final FeedProvider _feedProvider` field is removed entirely.
  - A getter `FeedProvider get _fp => widget.feedProvider` provides a clean
    shorthand throughout the state.
  - initState() no longer calls context.read() — it reads the provider from
    widget.feedProvider directly, which is always initialized.
  - _onFeedChanged, _search, and _buildBody all updated to use _fp.

lib/screens/home_screen.dart
  - The search button's onPressed reads the FeedProvider via context.read()
    BEFORE pushing (this context IS inside MultiProvider — that's the push site
    in MainShell → _AppRoot → AdBlockOverlay → ConnectivityOverlay → MultiProvider).
  - The resolved FeedProvider is passed to ContentSearchScreen as the
    feedProvider: parameter. The new route receives a live reference to the
    same FeedProvider instance — no duplication, no re-creation.
